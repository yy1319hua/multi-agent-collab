# 多 AI 协同入口

> 位置：`<工作区>/AGENTS.md`（**git 工作树之外**，不入库）
> 谁都能改，改完在底部「变更」追加一行。

## 你是谁、该做什么

你大概是被用户叫醒、接手某个项目的 AI。本文件告诉你在**这台共享工作台**上怎么干活。

工作区约定（工作区 = git 仓库的父目录，**工作树之外**）：

| 项 | 路径 |
| --- | --- |
| git 仓库 | `<工作区>/<repo>/` |
| 签到文件 | `<工作区>/CURRENT_AI` |
| 进度看板 | `<工作区>/PROGRESS.md` |
| 交接文档 | `<工作区>/HANDOFF.md`（工作树之外，**不入库**） |
| 凭据 | `<工作区>/creds/`（700/600，**绝不入库**）——放**真实凭据**：SSH 私钥、token、口令等 |
| 敏感串特征 | `<工作区>/credscan-patterns.txt`（每行一个正则，**绝不入库**）——只放**待拦截的正则形态**（内网 IP、内部域名等），不是凭据本身 |
| 工具 | `<工作区>/multi-agent-collab/scripts/` |

## 接手标准流程（每次都要走，别跳）

> 🔴 **进度属于仓库，不属于你的记忆。** 无论你是不是「刚经手的老 AI」、无论你觉得现场是什么样，
> 都必须真跑下面的 git 命令再决策。凭记忆直接续做会覆盖别人的里程碑。

### 贯穿纪律：锚定工作区，每步汇报（防漂移）

> 🔴 **你很可能正待在自己的本地 sandbox，而不是项目工作区。** 多 AI 共用的是
> `<工作区>/`（git 仓库的父目录），不是 AI 工具默认的本地目录。一旦漂移到错的地方写文件，
> 你就在别人的视线之外单干——签到、协同规范、强制钩子全部失效。

- **开工前先锚定**：`pwd` 确认自己在 `<工作区>/` 或其下的 `<repo>/`；并确认协同文件就位：
  `<工作区>/AGENTS.md`、`PROGRESS.md`、`HANDOFF.md`、`CURRENT_AI`、`LEASE_STATE`。
  找不到协同文件 → **视为漂移，立刻停下回报用户，禁止继续写任何文件**。
- **每完成一步都要汇报**（六步流程的每一步、以及此后每轮干活的任意动作）：
  ① **当前工作区绝对路径**（`pwd`）；② **协同文件状态**（上述文件是否就位、本步动了其中哪项）。
  这条汇报是锚点，让用户一眼确认你没漂走。
- `pwd` 一旦落在项目工作区之外（AI 默认 sandbox、临时目录、别的项目的目录等），
  **立刻停下、回报，不要**在陌生目录创建或修改任何文件。

### 第 1 步：签到

```bash
bash <工作区>/multi-agent-collab/scripts/lease.sh acquire <你的署名> "本轮用途"
cd <repo> && git config --local user.name "<署名>" && git config --local user.email "<署名>@local"
git config core.hooksPath .githooks
```

署名 = 产品名小写 + `-agent`。**不知道自己叫什么 → 拒绝开工，回报用户。**
签完把 `git config --get user.name` 放进回复用户的第一条消息，**让否决窗口打开**。

### 第 2 步：归档他人未提交改动

```bash
git status
# 有东西就：git add -A && git commit -m "wip: 接手 <上一位署名> 的未提交改动"
```

**禁止** `reset --hard` / `checkout --` / `clean -fd`。看着像垃圾的也可能是半成品。

### 第 3 步：对齐远端

```bash
git fetch && git log --oneline -5
```

**以此输出为唯一事实。** 凡与你的记忆/假设冲突，一律服从 git。

### 第 4 步：读现状

```bash
bash <工作区>/multi-agent-collab/scripts/doctor.sh
```

一条命令出齐：环境 / 签到 / 上一位遗留 / git 位置 / 看板 / 凭据扫描。

### 第 5 步：动手前对齐（治越界，必做）

先向用户复述「**我理解你要的是 X，范围到 Y 为止，不含 Z**」，拿到确认再写代码。
中途发现要偏离已确认范围 → **停下来重新确认**，不得自行扩大；
偏离部分即使写完也**不得并入已授权的 push**——`pre-push` 会按令牌范围拦截，
须另行请示后重新签发带新 `--paths` 的 `plan` 令牌。

### 第 6 步：收工

更新 `HANDOFF.md` → `push`（须有令牌：方案内改动用 `plan` 令牌，越界改动须另行请示）
→ 确认 `git status` 干净 → 汇报改动清单（`pre-push` 会打印本次推送文件清单）。

**收工判据（硬性）**：若在 `PROGRESS.md` 勾了任意一项，`HANDOFF.md` 的「已完成 / 下一步」
必须同轮改，否则算未收工。
**禁止写派生计数**（如「已完成 17/22 项」）——基数错了误差会一路传下去。要数字就现算。

```
署名：<你签的什么>

```

## 硬规矩

1. **单 AI 串行**。靠 commit 把进度留在仓库里；被硬中断时没提交的东西等于没做过。
   **commit 粒度按「可验证小步」走，不按看板条目走**——一条条目内部提交好几次是常态，
   判据是「现在被打断，这一步的产出值不值得留下」。别攒成一大坨再提交：
   攒得越大，中断一次丢的进度越多。
2. **署名**：第 1 步写入 `CURRENT_AI` + `git config --local`；用户可否决，立刻重签。
3. **push 须用户批准并签发令牌**。两种：
   - `batch` 逐次批准：一次推送有效，推后即消费，上次批准不延续。
   - `plan` 按方案授权：用户批准方案 = 授权该方案范围内的多次推送，
     但**每次 `pre-push` 都校验改动文件是否在批准范围内，越界即拒**——
     这是代码强制，不是文档承诺；默认 7 天过期，用户随时可 `--revoke` 撤回。
   **打 tag / 新分支首次推送 / 触发 CI 仍每次单独批准**。无令牌物理上推不上去。
4. **历史重写默认禁**：`filter-branch` / `rebase` / 强推 / `reset --hard origin/*`
   须用户事前单独批准，批准前先 `git bundle create` 存档。**AI 不自作主张修历史。**
5. **目录铁律**：只在授权目录内读写。
6. **私密信息不入库**：IP、域名、口令、私钥、token 不得进任何进 git 的文件，含 commit message。
   `pre-commit` 会扫描暂存新增行，命中即拒。
7. **方案先行**：新增功能 / UI 改动必须先出方案（必要时附效果图）交用户过目，
   拿到明确批准前禁止改代码、禁止打包。

关于「谁把关」的完整判定，见本框架的 `multi-agent-collab/references/CONFORMANCE.md`——
**注意：用户把关不是弱约束。代码能被 `--no-verify` 绕过，用户绕不过。**
