# 硬规矩：谁把关

不是所有规矩都要做成代码强制。判定标准是**按实际形态来定**，不是照抄某个框架。

## 核心判断

> 代码能被 `--no-verify` 绕过，**用户绕不过**。
> 所以在「用户全程在环、每步都要他点头」的场景里，**用户把关的执行力强于代码**。

这是本 skill 与一些自动化多 agent 框架的关键分歧：那些框架服务于无人值守场景，只能靠代码；
而多数真实项目是人类调度 AI，**把用户把关的条目标成"无强制"是本末倒置**。

## 判定表（按本 skill 的默认配置）

| # | 规矩 | 谁把关 | 说明 |
| --- | --- | --- | --- |
| 1 | 单 AI 串行 | 用户调度 | `lease.sh` 只记录签到信息，不拦截 |
| 2 | 署名 | 代码 | `pre-commit` 校验格式 + 与 `CURRENT_AI` 一致 |
| 3 | push 逐次批准 | 代码 + 用户 | `pre-push` 校验令牌；令牌须用户批准才签发 |
| 4 | 历史重写默认禁 | 用户 | 事前单独批准 + `git bundle` 存档 |
| 5 | 目录铁律 | 用户 | 授权制，越界即违规 |
| 6 | 私密信息不入库 | 代码 | `pre-commit` 第 4 条凭据扫描 |
| 7 | 新增功能/UI 改动先出方案与效果图 | 用户 | 没拿到「开工」就不能动代码——**这条比第 2、3 条更强** |

## 怎么给自己的项目做这张表

1. 列出你的硬规矩
2. 每条问一句：**违反它时，是谁/什么会拦下来？**
   - 有脚本或钩子拦 → 代码
   - 需要人点头才继续 → 用户（这不算弱）
   - 谁都拦不住 → **这才是真缺口**，优先补
3. 只对「谁都拦不住」的条目投入改造

## 常见误判

- ❌ 把「用户把关」当成没有强制 → 错，见上文
- ❌ 为每条规矩都写钩子 → 过度设计，且流程判断类（如"要不要重写历史"）硬做成代码反而僵化
- ❌ 照搬无人值守框架的标准 → 场景不同，结论会反过来
